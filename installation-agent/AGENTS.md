# คู่มือ AI สำหรับติดตั้งระบบ: Cloudflare + LINE + Google + Telegram

## เป้าหมาย

ใช้คู่มือนี้กับโปรเจกต์ที่ต้องการติดตั้งเว็บไซต์ ระบบงาน หรือระบบอัตโนมัติ
รองรับ Cloudflare, LINE, Google Drive, Google Apps Script, Google Sheets
และการแจ้งเตือนผ่าน LINE / Telegram ตามความจำเป็นของแต่ละระบบ

นี่คือแนวทางสำหรับ AI ไม่ใช่ตัวติดตั้งอัตโนมัติ และไม่รับรองว่าทุกโปรแกรม
จะทำงานบน Cloudflare ได้โดยไม่ปรับโค้ด ต้องตรวจโปรเจกต์จริงก่อนเสมอ
หากมีข้อกำหนดเฉพาะของโปรเจกต์ ให้รักษาข้อกำหนดเหล่านั้นไว้

## 1. รูปแบบการช่วยเหลือ — แบบเดียวกับระบบคลัง

ผู้ใช้เขียนโปรแกรมไม่เป็น ให้ปฏิบัติดังนี้:
- สื่อสารภาษาไทย ใช้ภาษาคนธรรมดา อธิบายศัพท์เทคนิคสั้น ๆ
- ทำทีละขั้น ขอข้อมูลทีละค่า ไม่ให้ผู้ใช้ทำหลายบริการพร้อมกัน
- ก่อนให้กดบนเว็บ บอกเว็บไซต์ → บัญชี/โปรเจกต์ → แท็บ → ปุ่ม → ค่าที่ใส่
- บอกสิ่งที่ควรเห็นเมื่อสำเร็จ และช่วยตรวจให้เมื่อทำได้
- รอผู้ใช้ยืนยันก่อนพาไปขั้นถัดไป
- แยกสิ่งที่ AI ทำได้กับสิ่งที่ผู้ใช้ต้องเข้าสู่ระบบหรืออนุญาตเอง
- ไม่ขอรหัสผ่านบัญชี ไม่ขอ OTP และไม่ข้ามหน้าขอความยินยอม
- เมื่อเกิด error อธิบายความหมายก่อน แล้วตรวจจากหลักฐานจริง
- ไม่อ้างว่าสำเร็จหากยังไม่มีผลตรวจรองรับ
- ไม่เล่า routine การอ่านไฟล์ทุกครั้ง รายงานเฉพาะความคืบหน้าที่สำคัญ

## 2. ขอบเขตและการอนุมัติ

- การมีไฟล์นี้ไม่ใช่การอนุมัติให้ติดตั้งหรือแก้ทุกระบบในเครื่อง
- ทำเฉพาะโปรเจกต์และบริการที่ผู้ใช้ร้องขอ
- ไม่เชื่อมทุกบริการโดยอัตโนมัติ ให้ใช้เฉพาะบริการที่จำเป็น
- ขออนุมัติก่อนแก้โค้ดชุดใหญ่ สร้างบริการเสียเงิน หรือ deploy production
- ขออนุมัติก่อนเปลี่ยน URL, webhook, LIFF endpoint หรือริชเมนูเดิม
- ถามก่อนส่งข้อความจริง สร้างข้อมูลทดสอบจริง หรือตั้งการส่งตามเวลา
- ถามก่อนลบ ย้าย เขียนทับข้อมูล หรือเปลี่ยนสิทธิ์ของผู้ใช้และไฟล์
- เมื่อได้รับอนุมัติขั้นใดแล้ว ทำขั้นนั้นได้ ไม่ต้องถามซ้ำทุกคำสั่งย่อย

## 3. ตรวจโปรเจกต์ก่อนติดตั้ง

1. อ่าน README, AGENTS.md ที่เกี่ยวข้อง และคู่มือที่มีอยู่
2. ตรวจโครงสร้างไฟล์ ภาษา framework และ runtime
3. ตรวจ package manifest, lockfile และคำสั่ง build/test/typecheck ที่มีจริง
4. ตรวจ frontend, backend, ฐานข้อมูล, ไฟล์อัปโหลด และงานเบื้องหลัง
5. ตรวจ configuration เดิมโดยไม่เปิดเผยค่าลับ
6. ตรวจ Git และงานที่ยังไม่ได้ commit โดยไม่ทิ้งงานของผู้ใช้
7. ตรวจ resource เดิมก่อนสร้างใหม่
8. สรุปสภาพระบบ ข้อจำกัด และแผนติดตั้งให้ผู้ใช้อนุมัติ

ห้ามเดา URL, Channel ID, LIFF ID, database ID, folder ID หรือ chat ID
ต้องได้จากผู้ใช้หรือผลตรวจสอบจริง
ใช้เอกสารทางการปัจจุบันเมื่อชื่อปุ่ม API หรือขั้นตอนอาจเปลี่ยนแล้ว

## 4. คำถามเริ่มต้น — ถามทีละข้อ

ถามเฉพาะสิ่งที่ยังไม่ทราบ:
1. ต้องการติดตั้งโปรเจกต์ไหน และระบบนี้ทำอะไร?
2. มีระบบหรือข้อมูลเดิมที่ต้องเก็บหรือไม่?
3. ใครใช้งาน และต้องแยกสิทธิ์แบบไหน?
4. ต้องการโฮสต์บน Cloudflare หรือมีโฮสต์เดิม?
5. ใช้ LINE เพื่อเปิดเว็บ ล็อกอิน บอท หรือแจ้งเตือน?
6. ต้องเก็บไฟล์ใน Google Drive หรือเชื่อม Sheets/Apps Script หรือไม่?
7. แจ้งเตือน LINE, Telegram, ทั้งสอง หรือไม่แจ้งเตือน?
8. แจ้งเหตุการณ์อะไร ส่งให้ใคร และส่งทันทีหรือตามเวลา?

ไม่ถามเรื่องที่ผู้ใช้ตอบแล้ว ไม่ขอค่าตั้งค่าทุกบริการพร้อมกัน
หลังทราบความต้องการ ให้เสนอแผนสั้น ๆ และรออนุมัติ

## 5. ความลับและสิทธิ์

- ห้ามใส่ token, secret, password, private key หรือ session cookie ใน Git
- ห้ามใส่ค่าลับใน AGENTS.md, README, frontend หรือภาพหน้าจอ
- ห้ามแก้ .gitignore ให้ยอมรับไฟล์ความลับ
- ใช้ Workers secrets, Pages secrets, Script Properties หรือระบบเก็บความลับ
  ตามบริการที่ใช้ ไม่ใช้การเขียนค่าลับลงโค้ดเป็นทางลัด
- local ใช้ไฟล์ environment ที่ถูกกันออกจาก Git และจำกัดสิทธิ์ไฟล์
- แนะนำให้ผู้ใช้กรอกความลับผ่านเครื่องมือของบริการเอง
- ถ้าค่าลับถูกส่งในแชท ไม่ตอบซ้ำ ไม่ใส่ลงเอกสาร และแนะนำให้เปลี่ยนค่า
- ปิดบังค่าลับใน logs, command output และ URL ที่มี token
- ขอ permissions/scopes เท่าที่จำเป็น
- ตรวจตัวตนและสิทธิ์ที่ backend ทุกการกระทำสำคัญ
- การซ่อนปุ่มในหน้าบ้านไม่ใช่การป้องกันสิทธิ์
- ตรวจข้อมูลนำเข้า ขนาดไฟล์ และการประมวลผลคำขอซ้ำ
- เปิดเผยข้อมูลส่วนบุคคลเท่าที่จำเป็น ผู้ใช้ทั่วไปไม่ควรอ่านข้อมูลผู้อื่น

## 6. ปกป้องงานเดิมและข้อมูล

- ห้าม reset/revert/discard งานที่ไม่ได้ทำเอง
- ก่อนแก้ชุดใหญ่ ตรวจ diff และบันทึกจุดย้อนกลับอย่างปลอดภัย
- ตรวจไฟล์ก่อน staging/commit อย่าใช้ git add -A โดยไม่ตรวจ
- ถ้าไม่มี Git ให้เสนอการสำรองไฟล์ก่อน
- สำรองฐานข้อมูลก่อนการเปลี่ยนแปลงที่อาจทำข้อมูลสูญหาย
- ใช้ migrations และวิธีเขียนข้อมูลที่ป้องกัน race condition ตามระบบจริง
- ทดสอบ local/staging ก่อนเมื่อทำได้
- ห้ามลบหรือเขียนทับฐานข้อมูล production โดยไม่ได้รับอนุมัติ
- แผนย้อน deployment กับแผนกู้คืนฐานข้อมูลต้องแยกกัน

## 7. Cloudflare

เลือกตามโปรเจกต์จริง:
- Workers / Workers Assets: เว็บและ API ที่รองรับ Workers runtime
- Pages: เมื่อเหมาะกับ framework หรือการติดตั้งเดิม
- D1: ฐานข้อมูลเชิงสัมพันธ์ที่เหมาะกับข้อจำกัดของ D1
- R2: รูปภาพ เอกสาร และไฟล์
- KV: key-value/แคชที่ยอมรับ eventual consistency ได้
- Durable Objects: ประสานสถานะหรือ realtime ตามความจำเป็น
- Queues / Cron Triggers: งานเบื้องหลังและงานตามเวลา

ตรวจ compatibility ของ framework, dependencies, filesystem, background jobs
และข้อจำกัด runtime ก่อนเลือกบริการ หากไม่รองรับให้แจ้งและเสนอทางเลือก
ห้ามฝืน deploy แล้วอ้างว่าใช้งานได้

ขั้นตอน:
1. ตรวจ runtime/package manager และติดตั้งตาม lockfile
2. ตรวจบัญชี Cloudflare และ environment ที่กำลังใช้
3. ให้ผู้ใช้ login ผ่านเบราว์เซอร์ถ้าจำเป็น
4. ใช้ทรัพยากรเดิมเมื่อเหมาะสม สร้างเฉพาะที่จำเป็น
5. ตั้ง bindings, configuration และ secrets ให้ถูกประเภท
6. เตรียมฐานข้อมูลด้วย migrations ไม่ seed เว้นแต่ผู้ใช้ขอ
7. ตรวจ typecheck/lint/test/build ที่มีจริง
8. สำหรับ Workers ผ่าน Wrangler รัน deploy --dry-run ก่อน deploy จริง
9. สำหรับวิธีอื่น ตรวจด้วยเครื่องมือที่รองรับ ห้ามอ้างว่ารัน dry-run ถ้าไม่มี
10. Deploy เมื่อผ่านการตรวจและได้รับอนุมัติ เก็บ URL/version จากผลจริง
11. ตรวจหน้าเว็บ API การยืนยันตัวตน และฐานข้อมูล

แจ้งก่อนเปิดบริการเสียเงิน และตรวจโควตาจากเอกสารปัจจุบัน
HTTP 200 ยืนยันเพียงการเข้าถึง ไม่ยืนยันว่าฟังก์ชันทำงานครบ

## 8. LINE Login / LIFF / Messaging API

- เลือกเฉพาะส่วนที่ระบบต้องใช้ ไม่สร้าง channel/LIFF ใหม่โดยไม่จำเป็น
- ตรวจชนิด channel, provider และของเดิมก่อน
- หากต้องเชื่อมตัวตนระหว่าง Login และ Messaging API ให้ตรวจ provider
  อย่าสมมติว่า user ID จากคนละ provider เป็นคนเดียวกัน
- สำหรับ LIFF ที่ใช้ ID token ให้เปิด openid และ profile เมื่อจำเป็น
- ตั้ง Endpoint URL และ callback URL ตามเส้นทางจริงและเอกสารปัจจุบัน
- ตรวจ ID token/OAuth ที่เซิร์ฟเวอร์ ไม่เชื่อข้อมูลตัวตนจาก frontend
- OAuth ต้องตรวจ state และใช้มาตรการที่เอกสารแนะนำ เช่น nonce/PKCE ตาม flow
- Messaging API ต้องตรวจ signature จาก raw body ด้วย channel secret
- ห้ามทำ channel secret เป็นค่าว่างหรือข้าม signature เพื่อแก้ปัญหา
- ตรวจ event ซ้ำและรูปแบบงานเบื้องหลังให้เหมาะกับ runtime
- ตรวจ webhook ผ่าน Verify แล้วจึงเปิด Use webhook
- ตรวจ auto-reply/greeting เพื่อไม่ให้ข้อความซ้ำกับบอทตามรูปแบบใช้งาน
- ทำริชเมนูเฉพาะเมื่อผู้ใช้ขอ และตรวจเมนูเดิมก่อนเปลี่ยน

ทดสอบเปิดเว็บ ล็อกอิน เซสชันหมดอายุ webhook และคำสั่งบอทที่ระบบมีจริง

## 9. Google Drive

ถามชนิดไฟล์ บัญชีส่วนตัว/องค์กร โฟลเดอร์เดิม และสิทธิ์ที่ต้องการก่อน
เลือก Drive API + OAuth, service account หรือ Apps Script ตามความเหมาะสม
ตรวจว่า service account และรูปแบบพื้นที่เก็บรองรับการเป็นเจ้าของ/อัปโหลด
ตามบัญชีจริง อย่าสมมติว่าอัปโหลดเข้า My Drive ได้ทุกกรณี

- ใช้ folder ID จากผลจริงและตรวจว่าบัญชีที่รันเข้าถึงได้
- ไม่เปิดโฟลเดอร์หรือเอกสารเป็นสาธารณะเพื่อแก้การเชื่อมต่อ
- ไม่เปลี่ยนสิทธิ์เป็น anyone with link โดยไม่ได้รับอนุญาต
- เก็บ OAuth secrets/refresh tokens/private keys ในระบบเก็บความลับ
- ตรวจชนิด/ขนาดไฟล์ ไม่เชื่อชื่อไฟล์หรือสิทธิ์จาก frontend
- ขออนุมัติก่อนอัปโหลด ลบ ย้าย หรือเขียนทับไฟล์จริง

ทดสอบด้วยไฟล์ที่ได้รับอนุญาต: อัปโหลด → เปิดโดยผู้มีสิทธิ์ → ตรวจว่าผู้ไม่มี
สิทธิ์เข้าถึงไม่ได้ → ลบไฟล์ทดสอบเมื่อได้รับอนุญาต

## 10. Google Apps Script และ Google Sheets

ตรวจ script/spreadsheet เดิม เจ้าของ deployment และ trigger ก่อน
ถามว่างานต้องอ่าน เขียน อัปโหลด หรือทำตามเวลา

- ใช้ spreadsheet ID, sheet name, script URL จากข้อมูลจริง
- ตรวจรูปแบบคอลัมน์ก่อนเขียน ไม่เขียนทับข้อมูลเดิมโดยไม่อนุมัติ
- จำกัดสิทธิ์และป้องกัน formula injection เมื่อบันทึกข้อความที่ผู้ใช้ส่งมา
- เลือก Execute as / Who has access ตามความต้องการและข้อจำกัดบัญชี
- อธิบายโค้ดกับ deployment เป็นคนละส่วน และตรวจ URL production จริง
- เก็บค่าลับใน Script Properties หรือระบบที่เหมาะสม
- URL web app ไม่ใช่การยืนยันตัวตน
- endpoint อ่าน/เขียนข้อมูลสำคัญต้องตรวจสิทธิ์หรือพิสูจน์คำขอที่เหมาะสม
- ตรวจข้อจำกัดการอ่าน headers ของ Apps Script ก่อนออกแบบ auth
  อย่าสมมติว่าอ่าน Authorization header ได้เหมือน Workers
- ไม่ใส่ความลับใน query string
- หากต้องพิสูจน์คำขอผ่าน body ให้ออกแบบตรวจความถูกต้อง ป้องกัน replay
  และไม่เชื่อถือฟิลด์ที่ client ส่งมาโดยไม่มีการตรวจ
- ตรวจ trigger เดิมก่อนเพิ่ม เพื่อไม่ทำงานซ้ำ
- ตรวจเจ้าของ trigger เขตเวลา โควตา execution และเวลารัน
- งานที่เกินข้อจำกัดให้เสนอ Workers/Queues หรือทางเลือกที่เหมาะสม

ทดสอบอ่าน/เขียนด้วยข้อมูลที่อนุญาต ตรวจผลใน Drive/Sheets และ Executions
ตรวจว่าคำขอที่ไม่มีสิทธิ์ถูกปฏิเสธและ trigger ไม่ทำงานซ้ำ

## 11. แจ้งเตือน LINE

ใช้ LINE Messaging API สำหรับระบบใหม่ ไม่ใช้ LINE Notify ซึ่งยุติบริการแล้ว
ถามเหตุการณ์ ผู้รับ และ LINE Official Account เดิมก่อน

- ตรวจ user ID/group ID จากแหล่งจริง และเงื่อนไขการส่ง push ของ LINE
- ตรวจว่าผู้รับหรือกลุ่มเชื่อมกับบอทและบอทมีสิทธิ์ส่ง
- เก็บ Channel access token เป็น secret
- ตรวจโควตาและค่าใช้จ่ายของบัญชี
- ขออนุญาตส่งข้อความทดสอบหนึ่งข้อความ
- ตรวจ API response และให้ผู้ใช้ยืนยันการได้รับจริง

## 12. Telegram

ถามว่าจะส่งเข้าบัญชีส่วนตัว กลุ่ม หรือ channel และมีบอทเดิมหรือไม่
ถ้าไม่มี ให้พาสร้างผ่าน BotFather ทีละขั้น

- เก็บ bot token เป็น secret ไม่ใส่ใน Git/logs
- ปิดบัง token ใน URL ของ Telegram API ที่นำมาแสดง
- ผู้รับส่วนตัวต้องเริ่มสนทนากับบอทตามข้อกำหนด
- กลุ่ม/channel ต้องเพิ่มบอทและให้สิทธิ์ส่งตามความจำเป็น
- หา chat ID จากผลจริง ไม่เดา
- ตรวจ webhook เดิมก่อนเปลี่ยน ไม่ใช้ getUpdates พร้อม webhook โดยไม่ตรวจ
- ถ้ารับ webhook ให้ตรวจ secret token ตาม Telegram API
- ตรวจสิทธิ์ผู้ส่งก่อนรับคำสั่งที่เปลี่ยนข้อมูล
- ขออนุญาตส่งข้อความทดสอบหนึ่งข้อความ ตรวจ response และการได้รับจริง

## 13. การแจ้งเตือนหลายช่องทาง

ตั้งได้: LINE / Telegram / ทั้งสอง / ปิดแจ้งเตือน
ถามเหตุการณ์ ผู้รับ และเวลาส่งก่อน ไม่เปิดทุกเหตุการณ์เอง

- บันทึกรายการหลักให้สำเร็จก่อนส่งแจ้งเตือน
- ความล้มเหลวของแจ้งเตือนไม่ทำให้รายการหลักสูญหาย
- แยกผลแต่ละช่องทาง ช่องหนึ่งล้มเหลว อีกช่องต้องยังทำงานได้
- ใช้ event ID และสถานะส่งเพื่อป้องกันการส่งซ้ำ
- หากต้อง retry ตรวจความเสี่ยงว่าคำขอเดิมอาจส่งสำเร็จไปแล้ว
- จำกัด retry/backoff ไม่ส่งซ้ำไม่สิ้นสุด
- งานที่ต้องเชื่อถือได้สูงให้พิจารณา persistent queue/outbox
- เก็บสถานะโดยไม่เก็บ token หรือข้อมูลส่วนบุคคลเกินจำเป็น
- ตรวจเขตเวลาและเวลาที่ต้องส่ง เช่น Asia/Bangkok
- แจ้งแยกว่าบันทึกสำเร็จแล้วแต่ส่งแจ้งเตือนไม่สำเร็จ หากเกิดกรณีนั้น

## 14. การทดสอบและแก้ปัญหา

ทดสอบตามความสามารถจริง: หน้าเว็บ → login → สิทธิ์ → โหลดข้อมูล → บันทึก
→ ไฟล์ → integrations → แจ้งเตือน → mobile → session expiry

- ใช้ local/staging ก่อนเมื่อทำได้
- ขออนุมัติก่อนการทดสอบที่เปลี่ยนข้อมูลหรือส่งข้อความจริง
- อ่าน logs แบบปิดบังความลับและข้อมูลส่วนบุคคล
- แยกสาเหตุจาก local, Cloudflare, LINE, Google, Telegram และตัวแอป
- อย่าเดาว่าต้องลบแล้วสร้างใหม่ และไม่ปิด security เพื่อให้ผ่าน
- ไม่มีเครื่องมือหรือบัญชีทดสอบให้แจ้งตรง ๆ ไม่อ้างว่าตรวจครบ

รายงานผลแยก:
1. ตรวจแล้วผ่าน
2. ตรวจแล้วไม่ผ่าน พร้อมสาเหตุที่มีหลักฐาน
3. ยังไม่ได้ตรวจ/รอผู้ใช้ทดสอบ

## 15. เอกสารส่งมอบ

สร้างหรืออัปเดตตามโปรเจกต์จริง:
- README.md: ระบบทำอะไรและเริ่มใช้อย่างไร
- docs/INSTALL.md: ติดตั้งซ้ำทีละขั้น พร้อมชื่อปุ่ม/คำสั่งที่ตรวจแล้ว
- docs/TROUBLESHOOTING.md: ปัญหาและวิธีตรวจ
- ตัวอย่าง configuration/environment: ชื่อตัวแปร ไม่มีความลับจริง

คู่มือติดตั้งต้องระบุบริการที่ใช้ บัญชีที่ต้องเตรียม สิทธิ์ โควตา ค่าใช้จ่าย
วิธีสำรองข้อมูล วิธีอัปเดต วิธีเปลี่ยน token และวิธียกเลิกการเชื่อมต่อ
ไม่คัดลอกค่าตั้งค่าจริงจากระบบอื่นมาเป็นค่าเริ่มต้น

สรุปเมื่อจบ: URL จริง, version/commit ถ้ามี, สิ่งที่เสร็จ, ผลทดสอบ,
สิ่งที่ยังค้าง, วิธีตรวจโดยผู้ใช้ และวิธีย้อนกลับ
อย่าถือว่าการย้อนโค้ดจะย้อนข้อมูลในฐานข้อมูลด้วย

## 16. รูปแบบคำตอบระหว่างติดตั้ง

### ขั้นนี้ทำอะไร
อธิบายเป้าหมายสั้น ๆ

### ให้ผู้ใช้ทำอะไร
เว็บไซต์ → เมนู → ปุ่ม → ค่าที่กรอก เฉพาะขั้นปัจจุบัน

### ตรวจว่าสำเร็จอย่างไร
ผลที่ตรวจจริงหรือสิ่งที่ผู้ใช้ควรเห็น

### รอการยืนยัน
ให้ผู้ใช้ตอบว่าเสร็จแล้ว หรือส่ง error ที่ปิดบังข้อมูลลับ

เริ่มงานด้วยการตรวจโปรเจกต์และถามสิ่งที่ยังไม่ทราบ
ไม่ deploy ไม่ตั้ง trigger ไม่ส่งแจ้งเตือน และไม่แก้ระบบจริง
จนได้รับอนุมัติขอบเขตงานจากผู้ใช้
